# 24小时原始数据采集检查

2026-09-24

## 结论

**标准100 Hz Raw采集模式具备连续24小时记录所需的计数及缓存容量，未发现该路径会因运行满24小时而发生数组越界或计数溢出。** 本结论基于代码检查和加速回归测试，尚未完成真实设备、无线链路及磁盘的24小时耐久试验，不能承诺零丢帧。

适用设置：工作台固件页“标准采集 · 单帧100 Hz / +2.5 dBm”，`ENABLE_RAW_DATA_PACKET=1`。PPG是否开启按实验条件固定；勿选射频复位三轮或功率切换实验。恢复原始信号仅修改上位机，本次没有修改或烧录固件。

## 仍需注意的边界

- **无线长断链不是普通回绕。** 序号差超过半周期（约327.68秒）时，现有算法不能可靠区分缺帧和乱序；跨过完整655.36秒周期也可能少算缺失。设备复位同样无法仅凭16位序号恢复。发生这类情况，应标记为中断并重新分段采集，不把拼接时间轴当作连续实测时间。
- **Time(s)是标称采样时间。** 固件Raw序号在主循环完成帧时递增，主循环或采集故障可能无法全部表现为序号缺口。应联合 `_status.csv` 的 SampleCounter、FrameCounter、ADC及发送错误检查，并对比 McuTime(ms) 和接收相对时间；晶振误差也不等同于真实秒长。
- **UI不能长期卡住。** 串口解析在线程中运行，但CSV写入在UI线程。Qt跨线程事件队列没有显式容量上限；磁盘阻塞或UI长期繁忙仍可导致排队增长。现有代码没有自动续录或磁盘满恢复机制。
- **flush并非断电保护。** 每秒级刷新Python文件缓冲有助于减少未写数据，但未执行逐包fsync，电脑断电或程序异常退出仍可能丢失尾部数据。
- **其他工作模式另评估。** 旧版固件心率算法的 `win_count` 为uint16_t，按1秒步长约18.2小时回绕，会影响窗口阶段判断；当前Raw模式不调用此算法。心率结果页还使用内存列表累积录制结果。本报告不为该模式作24小时保证。

## 建议的静置实验执行方式

1. 使用标准Raw模式，固定PPG状态、设备摆放、接收器距离和防风条件。若沿用本轮完整工作条件，确认PPG/IIC开启；历史热膜对照配置可能曾保存为关闭。
2. 电脑接电并关闭自动睡眠/休眠、避免USB接收器被系统挂起，录制期间避免重启或切换采集连接。设备电池续航按实际负载另行确认。
3. 使用本地磁盘，建议至少预留5 GB。按已有记录的前1000行原始字段估算，24小时主CSV约1.11 GB；后期时间及索引位数增长、数值长度等会改变体积，按1–2 GB预算并留余量。状态文件另计。完整数据超过常见电子表格的单表行数，后续用Python分块读取。
4. 开始后观察数分钟，确认Raw和STATUS文件持续增长、接收率约100 Hz，记录起始时间。结束时先停止录制，确认文件正常关闭，再断开设备。检查ValidFlag、MissingBefore、解析无效包及固件错误计数。
5. **保留未经中值及带通处理的Ut1/Ut2原始mV。** 温漂分析应看慢变基线，不能沿用0.5 Hz高通去掉目标变化。后续可同时展示全程原始趋势与按分钟汇总结果，将开机预热段单独分析。
6. 同步记录室温，最好增加靠近器件的温度记录，并尽可能记录电池电压。只有电压时间序列时，应称为“室温环境下24小时静置漂移”；没有同步温度，不能计算可信的mV/°C温度系数，也不能把全部慢漂移归因于温度。
